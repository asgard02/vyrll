## 1. Pipeline actuel : détection et positions de recadrage

### Constats

* **Détecteur réellement utilisé par `collect_crop_positions` (smart crop mono) : MediaPipe Tasks `mp.tasks.vision.FaceDetector`, pas un détecteur OpenCV.** Le singleton est chargé à la demande avec delegate CPU et le fichier local `backend-clips/models/blaze_face_short_range.tflite` : [`render_subtitles.py:4500-4534`](../backend-clips/render_subtitles.py#L4500). C’est le modèle **BlazeFace short-range** (le code le nomme explicitement et documente son entrée 128×128) : [`render_subtitles.py:4530`](../backend-clips/render_subtitles.py#L4530), [`render_subtitles.py:4663-4673`](../backend-clips/render_subtitles.py#L4663). La dépendance déclarée est `mediapipe>=0.10.9` : [`requirements.txt:3-9`](../backend-clips/requirements.txt#L3).
* Le chemin mono est : `collect_crop_positions` appelle `detect_face_candidates_scored(..., require_eyes=True)` ; ce dernier appelle `detect_all_faces_mp(..., include_haar=False)` : [`render_subtitles.py:4253-4260`](../backend-clips/render_subtitles.py#L4253), [`render_subtitles.py:3632-3651`](../backend-clips/render_subtitles.py#L3632). MediaPipe reçoit une image RGB contiguë, appelle `FaceDetector.detect`, lit la bounding box et les keypoints, puis produit `(cx, cy, area_ratio, has_eyes)` normalisé ; l’ancre de recadrage est le milieu des yeux, légèrement corrigé par le nez : [`render_subtitles.py:4541-4576`](../backend-clips/render_subtitles.py#L4541), [`render_subtitles.py:4603-4630`](../backend-clips/render_subtitles.py#L4603). `detect_all_faces_mp` fait une passe plein cadre et, pour les sources larges, des fenêtres carrées glissantes remappées sur la frame : [`render_subtitles.py:4663-4696`](../backend-clips/render_subtitles.py#L4663), [`render_subtitles.py:4699-4764`](../backend-clips/render_subtitles.py#L4699).
* Fréquence : le pré-pass lit toutes les frames pour repérer les coupes, mais ne lance la détection que tous les `_PREFLIGHT_INTERVAL` frames (et sur une coupe). Avec les défauts `SMART_CROP_DETECT_INTERVAL=15` puis `max(8, 15 // 2)`, cela fait **toutes les 8 frames par défaut** : [`render_subtitles.py:3692-3695`](../backend-clips/render_subtitles.py#L3692), [`render_subtitles.py:4236-4259`](../backend-clips/render_subtitles.py#L4236). Les candidats yeux alimentent les locks par plan ; le résultat final de cette fonction est trois tableaux en mémoire `cx_smooth`, `cy_smooth`, `zoom_smooth`, et non un JSON : [`render_subtitles.py:4224-4226`](../backend-clips/render_subtitles.py#L4224), [`render_subtitles.py:4302-4489`](../backend-clips/render_subtitles.py#L4302).
* Le JSON de positions concerne le choix du split, pas les trois tableaux du smart crop mono. `determineRenderModeForClip` appelle `analyzeFaceCountForClip`, qui lance `render_subtitles.py … --analyze-faces` : [`server.js:7425-7432`](../backend-clips/server.js#L7425), [`server.js:7679-7718`](../backend-clips/server.js#L7679). L’analyse construit les médianes par côté au format `{"cx": <0..1>, "cy": <0..1>, "area": <ratio>}` : [`render_subtitles.py:5947-5978`](../backend-clips/render_subtitles.py#L5947), puis le serveur écrit exactement un tableau de ces objets dans `face-positions-<idx>.json` : [`server.js:7770-7786`](../backend-clips/server.js#L7770), [`server.js:7863-7875`](../backend-clips/server.js#L7863). Hors visio, `[0]` est la plus grande aire et `[1]` la seconde ; en visio, le serveur les trie gauche/droite avant l’écriture, et le renderer déduit top/bottom de `cx` : [`render_subtitles.py:5974-6001`](../backend-clips/render_subtitles.py#L5974), [`render_subtitles.py:6893-6900`](../backend-clips/render_subtitles.py#L6893).
* **OpenCV est néanmoins encore utilisé dans cette chaîne, mais pas comme détecteur principal.** `cv2` sert au décodage vidéo, au BGR→RGB et aux transformations d’image autour de MediaPipe : [`render_subtitles.py:4194-4239`](../backend-clips/render_subtitles.py#L4194), [`render_subtitles.py:4603-4610`](../backend-clips/render_subtitles.py#L4603). Surtout, il existe un fallback OpenCV Haar frontal/profil : les cascades sont chargées depuis `cv2.data.haarcascades` : [`render_subtitles.py:3494-3524`](../backend-clips/render_subtitles.py#L3494); `detect_face_candidates_scored` ne l’essaie que si MediaPipe n’a retourné aucun candidat et si `require_eyes=False` : [`render_subtitles.py:3654-3675`](../backend-clips/render_subtitles.py#L3654). Donc il ne peut pas produire les `eye_hits` du pré-pass, mais peut produire un `weak_hit` du fallback mono : [`render_subtitles.py:4258-4293`](../backend-clips/render_subtitles.py#L4258). Le chemin multi-face peut aussi inclure Haar par défaut, mais les appels smart-crop mono et analyse split cités ici le désactivent explicitement : [`render_subtitles.py:4704-4764`](../backend-clips/render_subtitles.py#L4704), [`render_subtitles.py:5908-5918`](../backend-clips/render_subtitles.py#L5908). Il n’y a pas de DNN OpenCV dans ce chemin. `opencv-contrib-python<5.0.0` est présent, notamment parce que MediaPipe l’amène transitivement et pour conserver les XML Haar : [`requirements.txt:3-8`](../backend-clips/requirements.txt#L3).
* `_temporal_eye_lock` ne détecte pas : il associe les candidats échantillonnés par géométrie et ses IDs sont locaux à l’appel : [`render_subtitles.py:3957-4011`](../backend-clips/render_subtitles.py#L3957). Les redétections split ont leur cadence propre dans le masque dynamique et les préflights ; elles ne changent pas le constat ci-dessus sur le pré-pass mono : [`render_subtitles.py:8017-8072`](../backend-clips/render_subtitles.py#L8017), [`render_subtitles.py:6827-6841`](../backend-clips/render_subtitles.py#L6827).
* `track_crop_at_output_frame` n’est pas dans `render_subtitles.py` et ne relance pas la détection : il est dans [`ffmpeg_burn.py:404`](../backend-clips/ffmpeg_burn.py#L404) et transforme les positions déjà calculées en rectangle de crop. `split_lock_top`/`split_lock_bot` sont des tableaux de locks, pas des fonctions de détection ; ils sont consommés dans le loop de rendu [`render_subtitles.py:8447-8455`](../backend-clips/render_subtitles.py#L8447).
* `stream_layout.py` est isolé du chemin talk (commentaire explicite [`stream_layout.py:3-6`](../backend-clips/stream_layout.py#L3)). Il a son propre FaceDetector BlazeFace CPU [`:70-139`](../backend-clips/stream_layout.py#L70), ses fenêtres de détection [`:476-543`](../backend-clips/stream_layout.py#L476) et neuf échantillons par clip (`_SAMPLE_COUNT=9`) [`:49-52`](../backend-clips/stream_layout.py#L49), [`:1601-1620`](../backend-clips/stream_layout.py#L1601).

Depuis le commit de référence `6b402e5` (3 novembre), seuls trois commits touchent les fichiers audités : `a11380f`, `d043fab`, `5f08df8` (10 novembre). Ils ajoutent des traces de holds, de pistes mono et de sondes split sous `CAMERA_DEBUG_TRACE=1`; ils n’ajoutent ni ArcFace, ni onnxruntime, ni persistance d’empreintes. En revanche, le `main` actuel contient aussi une pipeline caméra V2 déjà présente dans le diff depuis ce point : Face Landmarker/BlazeFace, association géométrique de pistes et échantillonnage à 5 Hz [`render_subtitles.py:5389-5444`](../backend-clips/render_subtitles.py#L5389). Ce n’est pas une identité biométrique, mais c’est un risque de confusion terminologique.

## Impact sur la phase 3 : YuNet + SFace (sans implémentation)

**Statut : en attente du feu vert légal (RGPD biométrie + licences).** Les paragraphes suivants décrivent seulement les branchements possibles ; ils ne valident ni les modèles, ni les poids, ni leur licence, ni le traitement biométrique.

| Sujet | Remplacement de MediaPipe | Complément de MediaPipe |
|---|---|---|
| Détection YuNet | Remplacer l’implémentation interne de `_detect_faces_mp_raw` et son chargeur `_get_mp_face_detector` par un chargeur/session YuNet ; conserver le contrat de sortie normalisé `(cx, cy, area_ratio, has_eyes)` ou faire évoluer explicitement tous les appelants. Points d’entrée : [`render_subtitles.py:4508-4534`](../backend-clips/render_subtitles.py#L4508), [`:4603-4630`](../backend-clips/render_subtitles.py#L4603), [`:4699-4764`](../backend-clips/render_subtitles.py#L4699). | Garder BlazeFace comme détecteur de cadrage et appeler YuNet seulement là où une bbox compatible avec SFace est nécessaire. Les bboxes YuNet doivent alors être normalisées au même contrat avant `detect_face_candidates_scored`, `assess_split_clean` ou l’analyse de split. Cela limite le changement de décision de crop, mais double le coût et peut produire des désaccords de détection. |
| Ré-identification SFace | YuNet seul ne remplace pas SFace : YuNet détecte, SFace compare des représentations. Dans un remplacement complet, les bboxes/landmarks YuNet alimenteraient SFace avant la fusion temporelle ; il faut redéfinir la stratégie actuelle d’ancre yeux BlazeFace, qui est utilisée par le mono : [`render_subtitles.py:4541-4576`](../backend-clips/render_subtitles.py#L4541). | Option la plus localisée : conserver MediaPipe/BlazeFace pour choisir les positions et calculer, sur les détections déjà acceptées, une représentation SFace éphémère pour ajouter un coût de similarité à l’appariement. SFace devient alors un complément d’identité, jamais la source des coordonnées sans décision explicite de bascule. |
| Où brancher l’identité | À couvrir aussi si YuNet remplace le détecteur : pré-pass mono `collect_crop_positions` → `detect_face_candidates_scored` ([`render_subtitles.py:4194-4293`](../backend-clips/render_subtitles.py#L4194), [`:3632-3689`](../backend-clips/render_subtitles.py#L3632)); analyse/gate split `analyze_face_count_for_clip` et `assess_split_clean` ([`render_subtitles.py:5802-6025`](../backend-clips/render_subtitles.py#L5802)); préflight split et ordre des locks ([`render_subtitles.py:6827-6900`](../backend-clips/render_subtitles.py#L6827)). | Pour corriger la confusion de personne sans remplacer la détection, brancher SFace après détection et avant les choix temporels : `_temporal_eye_lock` pour le mono ([`render_subtitles.py:3957-4011`](../backend-clips/render_subtitles.py#L3957)), puis l’association des paires/locks split ([`render_subtitles.py:6827-6900`](../backend-clips/render_subtitles.py#L6827)). Le JSON `face-positions-<idx>.json` reste limité à `cx`, `cy`, `area` : aucun embedding ni score ne doit y être ajouté ([`server.js:7770-7786`](../backend-clips/server.js#L7770), [`:7863-7875`](../backend-clips/server.js#L7863)). |

YuNet + SFace ne doivent donc pas être présentés comme une simple substitution « OpenCV à la place du détecteur actuel » : le détecteur actuel est MediaPipe/BlazeFace, et OpenCV/Haar n’est qu’un fallback limité. La trajectoire la moins invasive serait un complément sous flag, en mémoire uniquement, en conservant les coordonnées et les seuils de MediaPipe ; un remplacement YuNet ne doit être envisagé qu’après validation de parité (bboxes, keypoints, faux positifs, cadence et coût). Dans les deux cas, aucun embedding, crop aligné, distance ou identifiant biométrique ne doit atteindre JSON, log, base ou trace.

## 2. Données disponibles pour une empreinte

### Constats

* Oui, bbox et keypoints existent juste en amont : `det.bounding_box` et `det.keypoints` sont lus dans `_detect_faces_mp_raw` [`render_subtitles.py:4620-4629`](../backend-clips/render_subtitles.py#L4620). Les keypoints BlazeFace exploités sont œil droit, œil gauche, nez et bouche [`:4541-4576`](../backend-clips/render_subtitles.py#L4541). Ils sont ensuite réduits à `FaceCand`, donc bbox/keypoints complets sont perdus avant `_merge_face_candidates` et les appelants.
* Un alignement 5 points n’est pas disponible avec certitude dans le contrat actuel : le code atteste 4 points utiles (yeux, nez, bouche), mais ne documente pas ni ne conserve un cinquième point. Une ArcFace standard à cinq points nécessiterait soit de vérifier le 5e keypoint réellement fourni par ce modèle, soit un landmarker dédié. La V2 emploie déjà Face Landmarker si son modèle est disponible [`render_subtitles.py:4771-4798`](../backend-clips/render_subtitles.py#L4771), mais son résultat ne doit pas être supposé disponible sur macOS headless.
* L’image est déjà en mémoire à chaque appel de détection : `frame` dans `_detect_faces_mp_raw`; `small` dans `collect_crop_positions`; les frames de `_FrameBank` pour le masque split; les fenêtres décodées par `preflight_split_segments`; et chaque `frame` dans la boucle de rendu. Une empreinte peut donc découper une ROI sans relire la vidéo **si elle est calculée au même endroit que la détection**. Après `analyze_face_count_for_clip`, seules les coordonnées médianes survivent dans le JSON.

### Risques et questions ouvertes

Recadrer par aire carrée déduite de `area_ratio` (pratique actuelle de validation [`render_subtitles.py:6631-6637`](../backend-clips/render_subtitles.py#L6631)) ne remplace pas l’alignement 5 points et dégraderait fortement un comparateur. Décision ouverte : l’option P3 autorise-t-elle l’usage du Face Landmarker déjà livré, ou impose-t-elle de ne dépendre que de BlazeFace ?

## 4. Dépendances, image et ressources

### Constats

`requirements.txt` interdit explicitement un second paquet OpenCV : MediaPipe tire `opencv-contrib-python`; ajouter `opencv-python-headless` crée une collision dans `cv2/` [`backend-clips/requirements.txt:3-8`](../backend-clips/requirements.txt#L3). `onnxruntime` et `insightface` ne sont pas déclarés (recherche exhaustive dans les fichiers projet hors dépendances installées). Le Docker installe les requirements dans un venv [`backend-clips/Dockerfile:35-45`](../backend-clips/Dockerfile#L35). Railway a un worker unique, plafond configuré de 8 vCPU / 8 Go [`backend-clips/railway.toml:1-20`](../backend-clips/railway.toml#L1); l’autre environnement est le worker local macOS.

La piste « ONNX + `onnxruntime` direct » est techniquement cohérente : elle évite le paquet InsightFace et ses packs téléchargés automatiquement. `onnxruntime` CPU officiel est le package adapté à macOS/CPU ([documentation ONNX Runtime](https://onnxruntime.ai/docs/get-started/with-python)). Elle ne résout cependant ni l’alignement, ni la licence des poids, ni le RGPD.

### Estimations (à mesurer avant engagement)

Pour un petit modèle MobileFaceNet/SFace int8 : +30 à +80 Mo d’image Docker pour le runtime Python décompressé, plus environ 10 Mo de poids; +80 à +200 Mo RSS par processus au pic (runtime, session, buffers), hors MediaPipe et frames. Pour un ArcFace ResNet100 FP32 : le seul poids ONNX public du Model Zoo fait 261 Mo ([source et licence](https://huggingface.co/onnxmodelzoo/arcfaceresnet100-8/tree/main)); prévoir plutôt +300 à +400 Mo d’image et +350 à +600 Mo RSS. Ce sont des fourchettes d’architecture, pas des mesures sur Mac/Railway. Valider séparément AMD64 Railway et l’architecture du Mac, avec une session unique partagée par process et un nombre de threads borné : l’exécution CPU concurrence ffmpeg/MediaPipe.

Risque/question ouverte : la limite Railway déclarée est 8 Go, mais la mémoire réellement disponible au worker et le type de CPU du Mac ne sont pas attestés ici. Mesurer l’image construite, RSS à froid/chaud et latence par visage dans les deux environnements avant tout déploiement.

## 6. RGPD — signalement, pas de décision

La CNIL indique qu’un gabarit extrait pour comparer des visages est une donnée biométrique au sens du RGPD ([CNIL](https://www.cnil.fr/en/node/1112)). Une empreinte limitée à la RAM d’un job ne supprime pas nécessairement le besoin d’analyse juridique; aucune conclusion de conformité n’est rendue ici.

À ce stade, aucune empreinte n’existe dans le code. Les fuites à empêcher lors de toute P3 sont :

* `face-positions-<idx>.json`, créé par [`server.js:7769-7786`](../backend-clips/server.js#L7769) puis supprimé dans les `finally` [`server.js:9986-9989`](../backend-clips/server.js#L9986) et [`:11654-11657`](../backend-clips/server.js#L11654) ; ne jamais y ajouter vecteurs ou scores d’identité.
* sorties stdout/stderr et traces : `_camtrace` sérialise les champs fournis [`render_subtitles.py:1554-1568`](../backend-clips/render_subtitles.py#L1554); `CAMERA_DEBUG_TRACE=1` écrit un `.camtrace.jsonl` à côté du MP4 [`camera_debug_trace.py:15-57`](../backend-clips/camera_debug_trace.py#L15).
* debug V2 : `camera_debug_payload` sérialise pistes, bbox et états [`render_subtitles.py:5321-5386`](../backend-clips/render_subtitles.py#L5321), puis le serveur peut téléverser ce JSON dans R2 et exposer son URL [`server.js:994-10026`](../backend-clips/server.js#L9994) et [`:11678-11718`](../backend-clips/server.js#L11678). Ne jamais y ajouter embeddings, hash ou distances par identité.
* logs de rejet split (`faces`, crops) [`render_subtitles.py:6641-6655`](../backend-clips/render_subtitles.py#L6641), tests/outils de résumé de camtrace, erreurs process et tout futur métrique/telemetry.

Cible de conception : embeddings, crops alignés et tables de correspondance locaux à la mémoire du processus; effacement des références à la fin de la fenêtre; aucune écriture disque, JSON, base, log ou trace. Question Legal ouverte : base juridique, information des personnes, minimisation, DPIA et conservation des vidéos sources.

Risque : un simple ajout de champ au payload V2/camtrace ou un logger d’exception peut contourner cet objectif; un test de non-persistance devra inspecter fichiers temporaires, stdout et upload R2.

## 7. Coût CPU (estimation)

Fréquences réelles pour une fenêtre de 60 s : analyse serveur `--analyze-faces` = `int(60/1,2)` = **50** frames [`render_subtitles.py:5802-5828`](../backend-clips/render_subtitles.py#L5802); masque split rendu = **150** frames à 0,40 s ou **~172** à 0,35 s [`render_subtitles.py:8017-8042`](../backend-clips/render_subtitles.py#L8017); mono preflight = **225** points à 30 fps / 8 frames, avec décodage de toutes les frames [`render_subtitles.py:4210-4259`](../backend-clips/render_subtitles.py#L4210). La V2, si activée, échantillonne 5 Hz [`render_subtitles.py:5401-5433`](../backend-clips/render_subtitles.py#L5401), soit 300 points/minute.

Pour dix clips d’une minute et une empreinte calculée seulement sur les candidats existants : minimum analyse seule = 500 frames; V1 analyse + masque = 2 000 à 2 220 frames; V1 avec mono = environ 4 250 à 4 470 points de détection, avant de multiplier par le nombre moyen de visages. Hypothèse de travail non mesurée : 3–15 ms/visage pour un petit modèle CPU aligné, 15–50 ms/visage pour ResNet100. À 1,5 visage/point, sur le dernier scénario, cela donne respectivement **~19–101 s** ou **~96–335 s** de CPU additionnel cumulé; murale Railway peut être plus longue sous concurrence. Ce n’est qu’une estimation : aucune inférence ni benchmark n’a été lancée. Une P3 doit instrumenter durée/session/visage séparément sur Mac et Railway avant activation.

Risque/question ouverte : le nombre de visages candidats et le coût de l’alignement peuvent dominer ces bornes. Faut-il limiter P3 au chemin analyse/diagnostic (500 frames) avant d’envisager les prépasses de rendu ?

## Correction proposée au rapport Small Talk du 10 novembre

> La détection de visages utilisée par le chemin split est MediaPipe Tasks `FaceDetector` avec le modèle BlazeFace short-range (`backend-clips/models/blaze_face_short_range.tflite`), et non OpenCV. OpenCV intervient pour le décodage, les transformations d’image et le Haar optionnel hors analyse split ; `assess_split_clean` appelle explicitement `detect_all_faces_mp(..., include_haar=False)`.

## Recommandation

**No-go pour l’implémentation maintenant; go conditionnel pour une P3 de diagnostic en mémoire uniquement** lorsque les trois préalables sont réunis : (1) un poids précis avec licence commerciale documentée et validation Legal (ne pas employer les packs publics InsightFace), (2) validation Legal/RGPD du traitement biométrique éphémère et du non-logging, (3) traces P2 démontrant une permutation d’identité plutôt qu’un défaut de détection/crop. Le flag doit préserver exactement le comportement V1 lorsqu’il est coupé, sans toucher aux seuils `SPLIT_*`, tailles de crop, facturation ni `detectMoments`.
